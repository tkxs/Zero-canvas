## 实施目标

在不改变线上官网面板 JWT 行为、不影响其他 OAuth 客户端的前提下，为现有应用 OAuth 客户端 `zero-canvas-web` 补齐分组读取、Key 创建和 Key 删除能力。优先复用 `sub2api` 已有 OAuth、Key Service、软删除和缓存失效实现，不新增重复业务链路。

## 1. 仅扩展 Zero-canvas OAuth scope

修改 `E:\code\中转站\sub2api\backend\internal\service\app_auth_service.go`：

- 只在 `zeroCanvasAllowedScopes` 中增加 `groups:read` 和 `keys:write`。
- 保留现有 `profile:read`、`keys:read`、`offline_access`。
- 不修改共享 `appAllowedScopes`、其他 OAuth 客户端、token 格式、grant/session 或刷新协议。
- 更新对应单元测试，确认 `zero-canvas-web` 只允许约定的五个 scope，其他客户端行为不变。

完整 scope：

```text
profile:read groups:read keys:read keys:write offline_access
```

## 2. 复用现有 OAuth 创建 Key 路由

不在服务端新增重复的 `POST /api/v1/app/keys`。

保留已有接口：

```text
POST /api/v1/app/groups/:groupId/keys
Authorization: Bearer <app access token>
Idempotency-Key: <operation id>

{"name":"USA零画布"}
```

修改 Zero-canvas 的 `web/src/services/api/usa0-auth.ts`：

- 将创建请求从 `POST /api/v1/app/keys` 改为现有的 `POST /api/v1/app/groups/:groupId/keys`。
- `groupId` 放入 URL，body 只发送 `name`，保持服务端现有严格 JSON 约束。
- 保留现有运行时 Key 拆分、错误脱敏和创建操作记录。

## 3. 给现有 OAuth 创建路由补幂等处理

在 `sub2api` 现有 app 创建 handler 上复用项目已有 idempotency coordinator，但增加一个窄范围的 App OAuth 适配：

- 从 `AppAuthSubject.UserID` 取用户身份，不能使用官网 JWT 的 `AuthSubject`。
- 要求合法 `Idempotency-Key`，使用固定操作 scope，并把用户 ID 纳入键哈希，避免不同用户使用相同原始幂等键时冲突。
- 请求指纹绑定用户、分组 ID 和规范化后的名称。
- 同一用户、同一幂等键和相同请求返回第一次创建结果，不重复创建 Key；相同幂等键但请求内容不同返回冲突。
- 不记录 access token、完整 Key 或请求/响应正文到日志；复用现有短时幂等记录生命周期。
- CORS 精确允许 `Idempotency-Key` 请求头，其他 Origin 白名单逻辑保持不变。

不改变旧路由地址，也不新增兼容别名，降低线上路由和监控面变化。

## 4. 新增最小 OAuth 删除接口

在 `backend/internal/server/routes/app_auth.go` 添加：

```text
DELETE /api/v1/app/keys/:id
```

要求 `keys:write`。

在 `AppResourceHandler` 添加专用删除 handler：

- 从 `AppAuthSubject.UserID` 获取当前 OAuth 用户。
- Key ID 非正整数时返回 `400 invalid_key_id`。
- 调用现有 `APIKeyService.Delete(ctx, keyID, userID)`，复用已有所有权校验、凭据墓碑软删除、认证缓存清理和创建尝试状态清理。
- 首次成功删除返回空的 `204 No Content`。
- 对不存在、已经删除或不属于当前用户的 ID 统一返回空的 `204`，既支持重复删除，也不暴露资源是否存在。
- 只有存储或缓存等非预期内部故障返回脱敏后的 `500`；不得直接返回 `err.Error()`。
- 不修改官网面板原有 `DELETE /api/v1/keys/:id` 的 200/403/404 行为。

基于“尽可能少修改”的要求，不新增仓储删除方法，也不改变现有 `APIKeyService.Delete` 公共语义；仅在 App OAuth handler 边界转换响应。

## 5. 对齐响应、CORS 和前端错误

- 保留 `/app/groups` 当前裸数组响应；Zero-canvas 已兼容裸数组和分页对象。
- 保留 `/app/keys` 当前 `{items,total}` 响应。
- 创建继续返回现有 app envelope，Zero-canvas 使用现有解包逻辑。
- 删除严格返回无 body 的 `204`。
- `success:false`、权限不足和无效响应继续由 Zero-canvas 转成明确错误，不再出现 `result.items is not iterable`。
- 更新 `docs/sub2api-zero-canvas-integration.md`，把创建路径改成服务端已有的 group-scoped 路径，并记录删除接口和幂等要求。

## 6. 聚焦验证

在 `sub2api` 补充或更新以下测试：

- `zero-canvas-web` 接受五个约定 scope，拒绝未授权 scope。
- 没有 app token 返回 `401`；缺少 `keys:write` 返回 `403`。
- 创建仅接受 URL 中的 group ID 与 body 中的 name。
- 相同幂等键和请求只创建一次；不同用户可使用相同原始幂等键；同键不同请求返回冲突。
- 删除本人 Key 后返回 `204`，Key 被软删除且旧凭据缓存失效。
- 重复删除、不存在、已删除和他人 Key 均返回不可区分的 `204`，他人 Key 不受影响。
- 非法 ID 返回 `400`，内部错误返回脱敏 `500`。
- CORS 只为已登记 Origin 放行 `Authorization`、`Content-Type` 和 `Idempotency-Key`。
- 官网面板原有创建/删除测试保持通过。

按 Zero-canvas 项目约束，不执行其构建、测试或类型检查；`sub2api` 是否运行其聚焦 Go 测试按实施授权执行。

## 7. 部署与重新授权顺序

1. 先部署或重建本地 `sub2api`，确认新 scope、幂等创建和删除路由可用。
2. 再更新 Zero-canvas 创建路径。
3. 在 Zero-canvas 中退出登录并重新走 OAuth 授权；旧 refresh token 不会自动增加 scope。
4. 验证分组读取、创建、同步、删除和重复删除。
5. 本地确认后，线上仅发布上述增量服务端改动；现有官网面板和其他 OAuth 客户端无需迁移。
